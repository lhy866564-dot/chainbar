# 设计说明

这份文档只记录「为什么这么设计」，运行步骤与接口清单见根目录 README，避免两处重复。

## 1. 为什么从「吧 → 分区」改成「论坛 → 技术 / 生活」

最早的版本照贴吧做成了四级结构：吧、吧内分区、主题帖、楼层。实际用下来，四个吧（技术交流、数码二手、校园生活、读书换书）里有三个其实在描述同一件事——「东西怎么流转」，只有技术交流是纯讨论。层级越多，用户越要在「先选吧再选分区」里做无意义的判断。

所以改成两块：**内容性质只有两种**（技术、生活），做成论坛下的两个模块；**东西的流转只有两种**（换、买），做成好物下的两个模式。表结构上 `sections` 只留两个固定 code，`threads` 用 `section_id` 归属，层级从四级降到三级，发帖时不用再选吧。

代价是失去了「自建圈子」的扩展性。要加新圈子时得改 `sections` 并决定它归到哪一类，而不是让用户随便建吧。对这个规模的项目，这比多一层选择更划算。

## 2. 好物为什么用「一个表 + mode 字段」而不是两张表

换物和购物共享大部分字段：标题、描述、分类、成色、发布者、状态、浏览数。差别只在三点：购物有价格，换物有「想换什么」；购物走链上托管，换物走申请协商。

拆成两张表会让「好物列表」的筛选（模式 + 分类 + 排序 + 关键词）变成两条 SQL 再合并排序，分页也会变难。所以留一张 `goods`，用 `mode` 区分，支付相关的字段允许为空。真正的流程差异放在两张流程表里：购物走 `trade_orders`（对应链上托管），换物走 `swap_requests`（纯库内状态机）。

## 3. 换物为什么要「接受时自动拒绝其他申请」

一件东西只能换给一个人。如果接受后其他申请还停在 `pending`，发布者会收到一堆已经没意义的待处理项，申请方也不知道自己落选了。

所以接受一个申请时在同一个事务里做三件事：该申请置 `accepted`、同件其他 `pending` 置 `declined`、好物置 `locked`。这样「一件物品同时被两个人换走」在数据层面就不可能发生。

## 4. 为什么好友关系单独一张表，私聊还要再校验一次

`friends` 存 `(requester, addressee, status)`，是为了让「谁申请的」这件事有方向：申请方向决定谁能同意，删除时也不用猜。私聊在发消息前会再查一遍 `areFriends`，看起来重复，但实时通道和 REST 是两条入口，任何一条漏校验都会让「非好友也能私聊」。校验放在 service 层，两条入口共用同一个函数。

## 5. 私聊为什么要把分享卡片存成 JSON

分享的本质是「一条消息 + 一个指针」。如果只存文本 `[分享] 标题`，对方点不进原帖；如果把帖子内容复制进消息，原帖改了就对不上。

所以 `direct_messages` 用 `msg_type` 区分文本与分享，`payload` 存 `{kind, id, title, extra}`——kind 决定跳转到帖子还是好物，id 决定跳到哪一条。列表预览直接用落库的文本，渲染时再解析 payload 画成卡片。

## 6. 论坛大厅和私聊为什么还是两张表

大厅是「一个频道多个听众」，天然按频道聚合，历史一次拉最近 100 条；私聊是「两个人一条线」，查询是 `(sender, receiver)` 的或关系，还要算未读数。合成一张表会让两边的索引互相拖累。

实时通道只做「送达」，落库仍然走 SQL：消息一定先写库再广播，刷新页面、换设备都能从历史里补回来。

## 7. 交易为什么先写库再上链

链上要一个唯一单号，库里自增主键正好能当这个号。做法是：先插入 `trade_orders` 拿到 id，再用这个 id 调 `createTrade`，成功后把交易哈希写回同一行。

链上调用失败时会把订单置为 `cancelled`、商品恢复 `on_sale`。不做这个补偿，就会出现「库里说已锁单、链上一分钱没有」的悬空订单，后面发起争议时合约会直接以 `Order missing` 回滚。

## 8. 合约为什么只记状态和金额，不记商品内容

商品标题、描述都可能被改、被删，链上写不下也不该写。合约只存 `itemHash`（后端用单号 + 商品信息算出的 SHA-256），作用是出纠纷时能比对「下单那一刻的商品是不是现在这个」。

## 9. 争议裁决为什么用「退款金额」而不是「谁赢」

现实里的纠纷很少是非黑即白：可能是部分退款、可能是扣一部分违约金。所以签名是 `resolveDispute(orderId, sellerWins, refundToBuyer)`——`sellerWins` 只用于事件里记录裁决结论，真正分钱的是 `refundToBuyer`：退给买家这么多，剩下的扣 1% 服务费给卖家。部分退款、全额退款、全额给卖家三种结果都能表达，不用为每种情况加一个函数。

## 10. 好友转账为什么复用链上，而不是只记一条流水

只写库的话「转账」就只是一行数字，没有任何可验证的东西。所以转账真的走一笔链上交易：后端托管账户向对方钱包转测试币，拿到哈希后落 `transfers`。失败也会落一行 `failed`，避免用户以为转成功了却查不到记录。

这也带来一个明确边界：转账是测试币，出款账户是演示账户，不对应真实资产。

## 11. 反馈为什么要带「状态 + 管理员回复」而不是直接进待办

反馈的价值在于闭环：用户提了、管理员看到了、排期了、做完了。只存一段文字的话，用户永远不知道自己的建议去哪了。所以 `feedback` 有 `type`（Bug / 功能建议 / 内容问题 / 其他）、`status`（待处理 / 处理中 / 已排期 / 已完成 / 已关闭）、`admin_reply` 与 `replied_by`，用户在设置页就能看到管理员回复。

## 12. 演示账户的取舍

本地测试链上没有真实用户钱包，如果强制要求每个用户自己签名，体验会变成「先装 MetaMask、再切网络、再点确认」。所以演示模式由后端账户代买家付款、代为转账，用一笔钱跑通整条链路。

这个取舍的边界很清楚：私钥在后端 `.env` 里，只对本地测试链有意义。README 的已知限制里写在第一条，就是为了避免有人把它当成生产方案。

## 13. 编译目标为什么降到 paris

solc 0.8.28 默认按 Cancun 编译，动态数据的内存复制会用到 `MCOPY` 指令。部分测试链节点还不支持这个指令，表现是「调用直接回滚，且没有 revert 原因」，连 struct getter 都回滚，很难排查。显式指定 `evmVersion: 'paris'` 后同样的代码在 Ganache 上正常，也不影响功能。

## 14. 前端为什么还是原生 JS 单页

四个模块的界面都是「列表 + 筛选 + 详情」，没有复杂状态。引入构建链（Vue / React + 打包）会让「克隆下来就能跑」变成「先装依赖、再等编译」。当前的做法是一个 `index.html` 加一个 `app.js`，由后端静态托管，改完刷新即可。

代价是渲染逻辑全靠手写模板字符串，页面变复杂后维护成本会上升。到那时再拆组件更合理。
