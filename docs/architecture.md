# 设计说明

这份文档只记录「为什么这么设计」，运行步骤与接口清单见根目录 README，避免两处重复。

## 1. 论坛为什么按「吧 → 分区 → 主题帖 → 楼层」拆

贴吧的结构不是拍脑袋分的，而是三种不同的数据：吧是长期沉淀的圈层（成员、帖子总量），分区是同一圈层里的话题切分（求购 / 出售 / 求助），主题帖是一次对话，楼层是对话的时序记录。

对应到表：`bars` 存聚合计数，`sections` 只存归属与排序，`threads` 存标题与正文，`posts` 只存回复。这样列表页只查 `threads` 加两个计数，不会把回复内容一起拉出来；楼层号用 `reply_count + 2` 计算（主楼算 1 楼），配合 `(thread_id, floor_no)` 唯一键，即使并发回帖也不会撞号。

## 2. 聊天为什么群聊和私聊分两张表

群聊是「一个吧多个听众」，天然按 `bar_id` 聚合，历史按吧拉取；私聊是「两个人一条线」，查询条件是 `(sender, receiver)` 的或关系，还要算未读数。合成一张表会让两边的索引互相拖累，所以拆成 `chat_messages` 与 `direct_messages`。

实时通道只做「送达」，落库仍然走 SQL：消息一定先写库再广播，这样刷新页面、换设备都能从历史里补回来，不会出现「聊天记录只在内存里」的情况。

## 3. 交易为什么先写库再上链

链上要一个唯一单号，库里自增主键正好能当这个号。做法是：先插入 `trade_orders` 拿到 id，再用这个 id 调 `createTrade`，成功后把交易哈希写回同一行。

链上调用失败时会把订单置为 `cancelled`、商品恢复 `on_sale`。不做这个补偿，就会出现「库里说已锁单、链上一分钱没有」的悬空订单，后面发起争议时合约会直接以 `Order missing` 回滚。

代价是短暂存在 `pending` 状态的订单。这个状态是给补偿逻辑用的中间态，正常路径上几十毫秒就过去了。

## 4. 合约为什么只记状态和金额，不记商品内容

商品标题、描述、图片都可能被改、被删，链上写不下也不该写。合约只存 `itemHash`（后端用单号 + 商品信息算出的 SHA-256），作用是出纠纷时能比对「下单那一刻的商品是不是现在这个」，而不是把商品搬上链。

## 5. 争议裁决为什么用「退款金额」而不是「谁赢」

现实里的纠纷很少是非黑即白：可能是部分退款、可能是扣一部分违约金。所以函数签名是 `resolveDispute(orderId, sellerWins, refundToBuyer)`——`sellerWins` 只用于事件里记录裁决结论，真正分钱的是 `refundToBuyer`：退给买家这么多，剩下的扣 1% 服务费给卖家。这样部分退款、全额退款、全额给卖家三种结果都能表达，不用为每种情况加一个函数。

## 6. 演示账户的取舍

本地测试链上没有真实用户钱包，如果强制要求每个用户自己签名，体验会变成「先装 MetaMask、再切网络、再点确认」。所以演示模式由后端账户代买家付款，用一笔钱跑通整条链路。

这个取舍的边界很清楚：私钥在后端 `.env` 里，只对本地测试链有意义。README 的已知限制里把它写在第一条，就是为了避免有人把它当成生产方案。

## 7. 编译目标为什么降到 paris

solc 0.8.28 默认按 Cancun 编译，动态数据的内存复制会用到 `MCOPY` 指令。部分测试链节点还不支持这个指令，表现是「调用直接回滚，且没有 revert 原因」，很难排查。显式指定 `evmVersion: 'paris'` 后同样的代码在 Ganache 上正常，也不影响功能。
